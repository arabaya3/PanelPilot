## Run history (harness issues, not product failures)

1. First dry run: 4 checks failed because the script looked for the full 64-hex hash (exports print a 12-hex prefix, `design 40beff92fcac`), read `export_status` as a string (it is `{label, identity}`), and matched "review approved" case-insensitively (the DXF title block has a field _label_ "Review approved" with an empty value on unapproved revisions; the stamp is `REVIEW APPROVED — STUDY, NOT FOR EXECUTION`). Checks corrected.
2. Run 1 (with rotation): 6 rows failed with `429 rate_limited` from `DESIGN_POLICY` (240 design requests per 5 min per tenant) because dry run + run 1 exceeded the budget. That is the throttle working, not an attack result. The script now waits out a design-endpoint 429 (Retry-After) and retries; in the final run it needed 0 retries. Rotation rows 4.6a/4.6b of run 1 were unaffected and PASS.
3. Final run: 42/42 PASS; plus 4.6a/4.6b from run 1 = 44/44 PASS.

## Rotation (4.6): how it was forced

Genuinely, by waiting: account B signed in twice (S1, S2); S1's young cookie was refreshed once (kept, `ROTATE_AFTER` = 5 min), then the script slept 310 s and refreshed S1 with its original cookie -> 200 with a new cookie (rotated). After 12 s (past `REFRESH_REUSE_GRACE` = 10 s), the stale original cookie was replayed with no bearer -> 401 `session_ended`; S1's new cookie and access token then got 401 (session ended), while S2 refresh and API calls stayed 200.
